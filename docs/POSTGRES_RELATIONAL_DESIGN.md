# Проект реляционной базы Rozephyr Learning

## Статус

Рабочее приложение переключено на реляционную схему `db/002_relational_core.sql`–`db/016_activity_history.sql`. Данные перенесены в отдельную PostgreSQL; старая база с `nexus_entities` сохранена как архив. Основной запуск использует новый API и ограниченную роль базы. Ниже описаны устройство схемы и инструменты переноса.

Текущая учётная запись `mentor` должна стать ментором существующего курса. Администратор платформы — новая отдельная роль. Она управляет предоставлением прав на платформу и не получает автоматический доступ к содержимому чужих курсов и результатам учеников. Учётная запись может иметь несколько ролей, но сама роль администратора не даёт прав ментора в курсе.

## Модель данных

| Область | Таблицы | Назначение и ключевые связи |
|---|---|---|
| Вход и роли | `platform_accounts`, `platform_account_roles`, `platform_credentials`, `account_sessions` | Одна учётная запись может иметь несколько ролей. Хеш и соль пароля отделены от профиля; в сессии хранится хеш токена, срок и отзыв. |
| Курсы | `courses`, `course_mentors`, `course_students`, `student_mentors` | Курс принадлежит ментору. У курса может быть несколько менторов; ученик может состоять в нескольких курсах и иметь нескольких закреплённых менторов. Составные ключи не позволяют назначить ментора из другого курса. |
| Учебный план | `course_modules`, `course_topics`, `course_lessons`, `lesson_versions`, `module_prerequisites`, `lesson_prerequisites`, `module_applications`, `topic_objectives`, `lesson_objectives` | Модуль, тема и урок принадлежат курсу; версия урока и исходный промпт сохраняются отдельно. Зависимости привязаны к тому же курсу. |
| Карта знаний | `course_skills`, `skill_relations`, `course_relations`, `relation_knowledge_transfers` | Навыки, связи навыков и межпредметные связи хранятся раздельно. Статус решения и пояснения связи не смешиваются с доступностью урока. |
| Занятия и пробелы | `prompt_snapshots`, `lesson_attempts`, `lesson_question_results`, `knowledge_gaps`, `gap_rechecks` | Снимок привязан к версии урока и ученику. Вопрос идентифицируется попыткой и номером; повторная проверка связана с конкретным пробелом и попыткой того же ученика в том же курсе. |
| ДЗ | `homework_assignments`, `homework_submissions`, `homework_reviews` | Условие, ответы и история проверок разделены. Для решения ментора требуется назначение этого ментора ученику; самоотчёт хранится с другим источником. |
| Аттестации | `course_exams`, `exam_tickets`, `course_assessments` | Билеты принадлежат экзамену курса, попытки — ученику этого курса. Номер попытки уникален в пределах ученика и экзамена. |
| Библиотека и связь | `course_library_files`, `course_messages`, `course_audit_events` | Файл принадлежит курсу; его байты и SHA-256 хранятся в отдельных типизированных полях. Сообщения и аудит имеют привязку к курсу. |

Модель ещё требует расширения до полного покрытия всех полей из действующей базы: нельзя отбрасывать старые сведения, историю, версии, аттестации, граф и вложения только потому, что для них пока не добавлен столбец. Внешние исходные файлы, в том числе файлы формата JSON, могут сохраняться как оригинальные вложения; это не должно подменять типизированное хранение самой учебной информации.

## Правила доступа в приложении

1. Администратор может выдавать и отзывать право ментора. Само наличие роли администратора не позволяет читать курс, менять учебные материалы или видеть результаты.
2. Ментор создаёт свои курсы и получает права владельца. Другого ментора в курс назначает имеющий соответствующее право ментор этого курса.
3. Ментор с правом управления учениками зачисляет ученика в курс и закрепляет за одним или несколькими менторами курса. Проверка отчётов разрешена только ментору с соответствующим правом, закреплённому за учеником.
4. Ученик видит только свои данные и курсы, в которых активен. Он не получает доступ к чужим отчётам даже при подмене идентификатора в запросе.
5. Каждая операция определяет пользователя по серверной сессии и проверяет права на сервере. Выбор курса в интерфейсе не является проверкой доступа.

Проверки этих правил находятся в `src/server/repositories/courses.ts` и проверены на временной БД. `src/server/relational-api.ts` работает по пути `/api/relational` с отдельной сессией и cookie. Вход с CAPTCHA, создание менторов и учеников, курсы, библиотека, сообщения, профиль, отчёты, ДЗ, аттестации, импорт учебного пакета и основные операции учебного плана покрыты проверками. Управление отдельными существующими экзаменационными билетами ещё требует доработки и повторной приёмки.

При включённом новом API страница `/platform` предоставляет отдельный вход администратора, список менторов, создание учётной записи и отзыв или восстановление права ментора. Это отдельная часть текущего сайта; экран ментора и ученика пока не переключён. Ментор и администратор входят под разными учётными записями.

`npm run dev` и `npm run dev:relational` запускают сервер с новой базой, указанной в `.env.relational`: старые маршруты и доступ к прежним файлам данных отключены. Для этого режима подключены экраны ученика, ментора и администратора; учебный сценарий проверен в браузере на отдельной тестовой базе. Часть прежних операций ещё требует переноса и повторной приёмки.

Для отдельной реляционной базы команда `npm run db:relational:permissions` подготавливает ограниченную роль сервера. На время настройки задаются `NEXUS_TARGET_DATABASE_URL` с административными правами, `NEXUS_RELATIONAL_APP_USER` и длинный случайный `NEXUS_RELATIONAL_APP_PASSWORD` из символов латиницы, цифр, `_` и `-`. Роль может читать и изменять необходимые строки, но не менять схему, удалять строки или изменять журнал миграций. В `NEXUS_RELATIONAL_DATABASE_URL` для обычного запуска нужно указать именно эту роль, а не владельца PostgreSQL. Команда не использует и не изменяет существующие посторонние роли.

Системный администратор PostgreSQL, владелец компьютера или резервной копии технически может получить доступ к данным. Ограничения роли администратора платформы не являются защитой от администратора сервера; для внешнего использования нужны отдельные меры защиты и управление ключами.

## Индексы и обращения

- Уникальные и внешние ключи задают идентичность объектов и не позволяют соединить данные разных курсов. Индекс `(course_id, student_id, submitted_at DESC)` поддерживает журнал попыток ученика.
- Индекс `(mentor_id, course_id, student_id)` поддерживает поиск назначенных учеников; `(course_id, student_id, homework_id, submitted_at DESC)` — историю ответов на ДЗ.
- Индексы входящих сообщений, срока действия сессий, обратных зависимостей и целевых навыков ускоряют соответствующие выборки. Частичные индексы используются для непрочитанных сообщений и неотозванных сессий.
- Запросы должны принимать параметры через драйвер PostgreSQL, работать в транзакциях при нескольких связанных изменениях и никогда не принимать идентификатор текущего пользователя из тела запроса.
- До публичного запуска нужны измерения на реалистичном количестве курсов и учеников: `EXPLAIN (ANALYZE, BUFFERS)`, проверка индексов внешних ключей, параллельных обновлений, времени восстановления и размера резервных копий. Создание индекса само по себе не гарантирует ускорение.

## Перенос и эксплуатация

`npm run db:relational:preflight` только читает старую PostgreSQL и показывает количество данных и проблемные ссылки без вывода персональных значений. В исходных данных обнаружены четыре старых ДЗ без владельца. По решению владельца проекта их не переносили; исходные данные и резервные копии сохраняются.

Пробный перенос в отдельную базу выполняется одной транзакцией и проверяет состав записей, тексты уроков, оригиналы отчётов и содержимое файлов перед фиксацией. Автоматические тесты также проверяют синтетические отчёты и историю ДЗ. Четыре файла библиотеки имеют несовпадающие старые контрольные суммы: сохраняются реальные байты, фактическая и старая суммы, а расхождение отмечается. Полная сверка всех полей и проверка всех API на изоляцию двух менторов и нескольких курсов ещё нужны перед переключением. Резервные копии и проверка восстановления описаны в `NEXUS_RUNBOOK.md`. Рабочий сервер пока не переключён.

Для пробного копирования подготовлена команда `npm run db:relational:import`. Она принимает переменные окружения `NEXUS_SOURCE_DATABASE_URL`, `NEXUS_TARGET_DATABASE_URL`, `NEXUS_MENTOR_PASSWORD`, `NEXUS_STUDENT_PASSWORD`, `NEXUS_ADMIN_PASSWORD`; значения не передаются аргументами команды. Пароли ментора и ученика должны соответствовать прежним учётным записям, пароль администратора задаётся отдельно. Для согласованного исключения ДЗ без владельца устанавливается `NEXUS_EXCLUDE_UNOWNED_HOMEWORK=1`. Исходный сервер должен быть остановлен, целевая база — отдельной и пустой. Команда не переключает приложение. Если перенос прервался после установки схемы, целевую тестовую базу нужно создать заново; исходная остаётся неизменной.
